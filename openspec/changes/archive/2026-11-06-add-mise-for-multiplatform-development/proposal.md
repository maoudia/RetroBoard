# Proposal

## Why

Node and pnpm versions are pinned in three different places today (`package.json#engines` says `node: >=22`, `packageManager: pnpm@10.28.0`, and every workflow under `.github/workflows/` repeats `node-version: 24` and a `pnpm/action-setup` pin). A contributor setting up a new machine has no single command to get the right toolchain, and there is no CI job that enforces these versions match across platforms. `mise` (a single static binary) reads pinned tool versions from one file and installs or activates them per shell, on macOS, Linux and Windows, closing that gap without adding infrastructure.

## What Changes

- New `.mise.toml` pinning `node` (24, matching the workflows) and `pnpm` (10.28.0, matching `packageManager`) for local shells. `mise` reads `packageManager` for pnpm and does not need a separate pin for it when `node.compat=true`-style config is avoided; this proposal keeps both tools explicit in `.mise.toml` for clarity and because CI does not read `packageManager` today.
- New `mise.lock` (committed) for deterministic tool checksums across platforms, generated by `mise install`.
- New `docs/DEVELOPMENT.md`: one page with `mise install` setup for macOS, Linux and Windows (WSL), and what to do when `mise` is not installed (fall back to nvm/Volta + corepack, documented as the previous path).
- `README.md` quick-start gains a one-line mention of `mise install` as the recommended first step, keeping the existing manual steps as the fallback.

Out of scope (flagged as follow-up, not done in this change): a `mise-check.yml` validation workflow, a weekly tool-update workflow, and rewriting existing CI workflows to call `jdx/mise-action` instead of `actions/setup-node` + `pnpm/action-setup`. Editing `.github/workflows/**` needs its own explicit review (AGENTS.md); this change stays local-dev-only so CI behaviour is unchanged.

## Capabilities

### New Capabilities
None.

### Modified Capabilities
None. This is pure tooling/infrastructure: no product behaviour changes, so `skip_specs: true` is set in `.openspec.yaml`.

## Impact

- Bounded context: none (developer experience / build tooling, outside the product's bounded contexts in `docs/PLAN.md` section 4).
- Affected: repo root (`.mise.toml`, `mise.lock`), `docs/DEVELOPMENT.md` (new), `README.md` (one line).
- No code, no API, no dependency, no runtime behaviour touched. No relay traffic, no free-plan budget impact.
- CI workflows are not modified in this change (see "Out of scope" above).
